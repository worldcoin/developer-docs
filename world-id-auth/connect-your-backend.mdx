Connect your backend to the World ID issuer with OpenID Connect (OIDC).

Your backend is a confidential OIDC client that keeps its
credentials private. Browser-only, native, and CLI applications also need a backend for
this integration. If your auth server already handles sign-in for your application,
follow [Connect the World ID issuer to your auth server](/world-id-auth/connect-your-auth-server) instead.

Before you start, [register your application](/world-id-auth/app-registration) to
configure its callback URLs and client authentication and get its credentials.

## Configure your OIDC library {#configure-your-oidc-library}

| Setting               | Value                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------ |
| Issuer                | `https://auth.world.org`                                                                                           |
| Discovery             | `https://auth.world.org/.well-known/openid-configuration`                                                          |
| Response type         | `code`, with query response mode                                                                       |
| Scope                 | `openid`, optionally with `email`                                                                      |
| PKCE                  | `S256`, required                                                                                       |
| Client authentication | Your registered method; see [Client authentication](/world-id-auth/connect-your-backend#client-authentication) |

Read the endpoints and signing keys (`jwks_uri`) from the discovery document.
Turn off library defaults that add `profile`, `offline_access`,
`prompt=consent`, or `prompt=select_account`. Use registration, discovery, and
credentials from the same environment.

## Authenticate through the browser {#authenticate-through-the-browser}

Save fresh `state`, an optional fresh `nonce`, and the S256 PKCE verifier in
server-side state for each attempt. On success and error callbacks, validate
`state` and require `iss` to match the discovered issuer before redeeming the code.
Treat authorization errors as failure. Exchange the code with your registered
client-authentication method; each code expires after five minutes and can be
used once. [Validate the ID token](/world-id-auth/connect-your-backend#validate-the-id-token)
before finding the account by `(iss, sub)`.

The authorization request has these decoded query parameters. URL-encode them
with your library and generate fresh random values for each attempt:

```text
GET https://auth.world.org/api/v1/authorize
client_id=<portal-client-id>
redirect_uri=https://app.example/auth/world/callback
response_type=code
scope=openid
state=<fresh-random-state>
nonce=<fresh-random-nonce>
code_challenge=<base64url-sha256-of-verifier-without-padding>
code_challenge_method=S256
```

The PKCE verifier is a cryptographically random value of 43–128 characters; keep
it private until the code exchange. The token request is a form body, not JSON.
For a client registered with `client_secret_post`, its decoded fields are:

```text
POST https://auth.world.org/api/v1/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
client_id=<portal-client-id>
client_secret=<backend-secret>
code=<returned-code>
redirect_uri=https://app.example/auth/world/callback
code_verifier=<original-verifier>
```

For the portal's default `client_secret_basic`, remove the secret from the body
and send Basic authentication instead. For `private_key_jwt`, send the assertion
fields described under [Client authentication](/world-id-auth/connect-your-backend#client-authentication).
Never log request bodies, Authorization headers, or callback query strings.

The response contains `id_token`, an opaque `access_token`, `token_type`, and
`expires_in`. See [Token response](/world-id-auth/id-tokens-and-identity#token-response)
for each field and [Decoded ID token](/world-id-auth/id-tokens-and-identity#decoded-id-token)
for an example payload.

## Validate the ID token {#validate-the-id-token}

Validate every ID token with an OIDC library before using its claims. Merely
decoding a JWT is not validation. Check:

- **Issuer:** exactly `https://auth.world.org`.
- **Signature:** RS256 with a signing key from the discovery document's `jwks_uri`.
  Cache the JWKS with bounded refresh and handle signing-key overlap.
- **Audience:** your client ID.
- **Expiration:** reject the token after `exp`.
- **Nonce:** matches the value you sent, if you sent one.
- **Authentication context:** when you require freshness, check `acr`, `amr`, and
  `auth_time` as described in [Step-up authentication](/world-id-auth/step-up).

After validation, use `(iss, sub)` as the World ID account identifier; see
[Store and match sub](/world-id-auth/id-tokens-and-identity#store-and-match-sub).
Use `auth_time`, not `iat`, to check when the user authenticated: an existing
browser session can produce a new token without a new World ID proof. Issuer
sessions expire after 180 days without authenticated browser activity; activity
renews that deadline, while `prompt=login` and `max_age` still require fresh
authentication when requested.

## Primary sign-in {#primary-sign-in}

To use World ID as your application's primary or only sign-in, use the browser or device
flow in this guide. After validating the ID token, find or create your application's
account using `(iss, sub)` and issue your own session. See the
[claim reference](/world-id-auth/id-tokens-and-identity#claim-reference) for optional inbox email claims.

You can then add [step-up authentication](/world-id-auth/step-up) for
sensitive actions or [human checkpoints](/world-id-auth/human-in-the-loop)
for agent workflows. Both use the same OIDC connection.

## Client authentication {#client-authentication}

Authenticate at the token and device authorization endpoints with the client's
registered method:

| Method                                 | How to send credentials                                                                                                                                                     |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client_secret_basic` (portal default) | Form-encode the client ID and secret and send them in the Authorization header as Basic credentials. An optional body `client_id` must match.                               |
| `client_secret_post`                   | Send `client_id` and `client_secret` in the form body, without an Authorization header.                                                                                     |
| `private_key_jwt`                      | Send `client_id`, `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, and `client_assertion` in the form body, without an Authorization header. |

For `private_key_jwt`, register the public JWKS in the portal and keep the private
key in your backend. The assertion is a compact RS256 JWT:

- `kid` selects a registered RSA key (2048–8192 bits). It may be omitted when
  exactly one key is registered.
- `iss` and `sub` are both the client ID.
- The single `aud` is `https://auth.world.org` or the exact endpoint being called.
- Include `iat`, `exp` (at most one hour after `iat`), and a unique `jti` of at
  most 256 bytes. Expiration is strict; `iat` and optional `nbf` allow 30 seconds
  of clock skew.

Use a fresh assertion for every request, retry, and device poll, including after
`authorization_pending`. Assertions are single-use across endpoints. A rejected
assertion returns HTTP 400 `invalid_client`.

## Cross-App Access for agent hosts {#cross-app-access-for-agent-hosts}

Agent hosts request `openid offline_access` for delegation controlled by the user.
The human selects reviewed apps; new apps require explicit selection.
Authorization expires after 180 days without a successful token refresh or
ID-JAG exchange. Either renews that inactivity deadline, but neither proves fresh
World ID presence.

The host's authentication layer manages token exchange, refresh, and credentials.
Follow the [XAA guide](/world-id-auth/xaa) to configure an app's authorization
server, enroll the app, and understand user consent and revocation.
World ID authentication with `openid` remains unchanged.

## Recovery after interrupted requests {#recovery-after-interrupted-requests}

- **Code exchange returns HTTP 503 or times out:** You can retry a limited number
  of times before the code's original expiry, using the same code, redirect URI,
  and PKCE verifier.
- **Device poll fails:** Follow the
  [polling and stop rules](/world-id-auth/connect-your-backend#device-flow).
- **Exchange returns `invalid_grant`:** Treat it as failure.
  Start a new authentication attempt. Each code can be redeemed once. If a
  successful exchange's response was lost and you retained no tokens, you must
  also start again.

For [`private_key_jwt`](/world-id-auth/connect-your-backend#client-authentication),
generate a fresh assertion for every retry or poll, even after a signing failure.
Keep codes, assertions, tokens, PKCE verifiers, and client credentials out of logs.

Before retrying a payment or another external action, check your application's saved
status and use its idempotency controls.


## Limitations {#limitations}

- **Unsupported grants and request features.** Implicit and hybrid grants, client
  credentials, and request objects (`request` / `request_uri`) are not implemented.
  Refresh tokens and token exchange are available only for the XAA profile above.
- **Device flow and action approval.** See the
  [supported device profile](/world-id-auth/connect-your-backend#supported-device-profile)
  for request controls, parameter validation, and action-approval limitations.
- **Access tokens authorize UserInfo only.** The token response's opaque
  access token does not authorize calls to the World ID MCP server, your APIs, or
  downstream MCP tools. Protected downstream MCP tools require their own
  resource-bound access tokens and MCP OAuth integration, which device
  authorization does not supply. The World ID MCP server uses separate,
  renewable grants.
  Relying services own their accounts, API credentials, grants, eligibility,
  quotas, and redemption rules.
- **Delegation requires explicit XAA consent.** Consent for browser authentication
  is not a downstream agent grant. Reuse valid credentials issued by your
  application before starting another authentication attempt.
- **Issuer logout does not reach your application.** Ending the World ID issuer's
  browser session does not revoke your application's sessions, tokens, grants, or benefits.

## Troubleshooting {#troubleshooting}

OAuth failures include a human-readable `error_description` alongside `error` in
the JSON response or authorization error redirect. Use the description to diagnose
malformed parameters, and use the `error` code to decide how your application responds.
Descriptions never echo submitted values. A client or callback mismatch returns
an error without redirecting to your callback, using the same guidance for either mismatch.
Credential, grant, and service errors use deliberately generic descriptions.
Keep dependency failures distinguishable from invalid authentication.

| Symptom                                                           | Check                                                                                                                                                                                                                           |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `invalid_scope`                                                   | Request `openid` for World ID authentication or `openid offline_access` for XAA delegation when discovery advertises it; `email` is also accepted. Remove other library scopes.                                                 |
| HTTP 400 `unsupported_grant_type`                                 | Use a grant type advertised by discovery. Refresh and ID-JAG exchange are unavailable while XAA is disabled.                                                                                                                    |
| Authorization `invalid_request`                                   | Check the active client, exact registered callback, state, nonce, S256 challenge, response mode, and supported prompt. Bad client/callback requests fail without redirecting to your callback.                                  |
| `invalid_client` at token/device endpoint                         | Check environment, registered auth method, credential encoding, and that methods are not mixed. For JWTs check audience, key, expiry, and a fresh JTI per request. Basic failures use HTTP 401; POST/JWT failures use HTTP 400. |
| `invalid_grant`                                                   | Check expiry, single-use code, exact callback, PKCE verifier, and client binding. Do not blindly replay a possibly consumed code.                                                                                               |
| `login_required` / `interaction_required`                         | A `prompt=none` request cannot complete silently. Start an interactive request when appropriate.                                                                                                                                |
| `account_not_eligible` / `client_registration_disabled` in portal | Check participant Google-account eligibility and registration availability with the organizer/operator. These are not World ID proof failures.                                                                                  |
| HTTP 503                                                          | Treat as temporary unavailability, never invalid identity or successful approval. Use bounded requests; apply the device polling rules above.                                                                                   |

References: [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html),
[device authorization](https://www.rfc-editor.org/rfc/rfc8628.html).
