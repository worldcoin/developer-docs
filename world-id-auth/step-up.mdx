Step-up authentication requires recent World ID authentication before a sensitive action, such as a payment, redemption, or account change. Your backend validates the authentication result, links or matches the returned World ID to the application account, and checks permissions before allowing the action. This works with your existing sign-in or with World ID as your primary sign-in.

**Prerequisites:**

- An OIDC client registered in the developer portal. The production issuer is `https://auth.world.org`. Read endpoints from `https://auth.world.org/.well-known/openid-configuration`.
- A backend that runs the Authorization Code Flow with S256 PKCE and validates ID tokens.

## Implement step-up

1. **Save the pending operation.** Record the current application account, its linked World ID `(iss, sub)` if present, whether this attempt may enroll an identity, the required authentication age and class, and the pending operation in server-side state. Bind a fresh OAuth `state`, `nonce`, and PKCE verifier to this attempt.
2. **Request fresh authentication.** Redirect to the authorization endpoint with the usual browser authentication parameters plus `max_age=0` for fresh authentication, or a positive `max_age` for a maximum authentication age. For example, these additional decoded query fields require fresh Orb-class authentication:

   ```text
   max_age=0
   claims={"id_token":{"acr":{"essential":true,"value":"https://world.org/oidc/acr/orb"}}}
   ```

   The person can authenticate with an Orb proof or an enrolled passkey for an Orb-verified account.
3. **Validate the result.** Validate the callback `state`, redeem the code once, and validate the ID token, including its nonce. Reconfirm that the initiating session and target account match the saved attempt. For a linked account, require the returned `(iss, sub)` to match. For an unlinked account, continue only when the attempt explicitly permits enrollment and the identity isn't linked elsewhere.
4. **Check freshness and assurance.** Validate `acr`, `amr`, and `auth_time` against the saved policy. For `max_age=N`, check the authentication age when the operation runs, with only a small clock tolerance. For `max_age=0`, check that authentication belongs to the newly initiated attempt.
5. **Allow the operation.** After all checks pass, save the validated `(iss, sub)` for enrollment if needed, recheck permissions, and allow the intended operation. Cancellation, expiry, identity mismatch, unsupported assurance, and dependency failures leave the operation unauthorized.

## Request parameters

| Parameter | Behavior |
| --------- | -------- |
| `max_age=N` | Accept authentication no older than N seconds. N is a nonnegative integer. |
| `max_age=0` | Require fresh authentication for this transaction, even with an existing browser session. |
| `prompt=login` | Require fresh authentication. Overrides a larger `max_age`. |
| `prompt=none` | Forbid interaction. Returns `login_required` or `interaction_required` if silent authorization can't complete. |
| `acr_values` | Voluntary preferences. Unsupported values don't force an error. An empty value uses the client's [accepted accounts](/world-id-auth/accepted-accounts). |
| `claims` | Request an essential ID token `acr` to require an acceptable authentication class. |

The supported `prompt` values are `login`, `none`, and `consent`, supplied individually. `select_account` and prompt combinations are rejected.

A request with no `acr_values` and no `acr` claim request uses the client's [default accepted accounts](/world-id-auth/accepted-accounts#choose-the-default-accepted-accounts). If the default is **Any account**, the request also admits accounts without Orb or Selfie Check verification. Use explicit classes when the operation requires verification.

## Accept Orb or Selfie Check

To require Orb or Selfie Check verification, set the `claims` parameter to this JSON:

```json
{
  "id_token": {
    "acr": {
      "essential": true,
      "values": ["https://world.org/oidc/acr/orb", "https://world.org/oidc/acr/selfie"]
    }
  }
}
```

One matching class is enough. An essential `acr` claim accepts only the classes it lists. These baseline classes can also be satisfied by a passkey on a verified account. Add `max_age=0` for fresh authentication and check `amr` for the method used.

## Require Face Auth

To require Face Auth in the World ID app, send this JSON as the URL-encoded `claims` parameter:

```json
{ "id_token": { "acr": { "essential": true, "values": ["https://world.org/oidc/acr/orb-face"] } } }
```

Add `max_age=0` to require the check during this browser authentication attempt. Without a freshness requirement, a qualifying Face Auth session can be reused. `https://world.org/oidc/acr/selfie-face` requires the same check on a Selfie Check proof.

`acr_values=https://world.org/oidc/acr/orb-face` requests Face Auth whenever a new proof is created. Unlike an essential `claims` request, it permits reuse of a baseline browser session and acceptance of a baseline result. When listing multiple `acr_values`, put your preferred class first.

If none of the requested essential classes is supported, the request fails with `unmet_authentication_requirements`. A passkey login never reports a `-face` class. Check `amr` to see whether a World ID proof (`pop`) or a passkey authenticated the person.

## Device flow

The device authorization endpoint accepts the same `acr_values` and `claims` parameters. Device authentication always requires fresh authentication, so `prompt` and `max_age` don't apply. If the mobile response can't satisfy an essential requirement, token polling returns `access_denied`.
