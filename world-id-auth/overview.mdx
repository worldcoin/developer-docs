**Human continuity for apps and agents.**

Recognize the same human across accounts, devices, and agents through a private identifier unique to your application.

[Read integration guides →](/world-id-auth/quickstart)

## Human continuity {#human-continuity}

Human Continuity gives your application a stable way to recognize the same human across their accounts, devices, and agents while preserving privacy.

Welcome people back, carry reputation forward, and create experiences that grow more valuable with every interaction.

## What you can build {#use-cases}

### Build durable reputation

Let credibility, contribution history, and community standing grow over time using a private identifier scoped to your sector.

### Protect scarce benefits

Apply eligibility, claim limits, and participation rules consistently across every interaction with the same human.

### Power human-backed agents

Give agent experiences a persistent connection to the human who authorized them, with fresh authentication for important actions.

### Recover established accounts

Reconnect a returning human to their account in your application from a new device through the same continuity identifier.

### Enforce lasting consequences

Carry suspensions, bans, and trust decisions across accounts, devices, and agents linked to the same continuity relationship.

## Private recognition {#pairwise-subjects}

Applications registered in the same **sector** receive the same stable identifier for a given World ID account. Applications in different sectors receive different identifiers.

**One World ID account, viewed by three applications**

| Application | Identifier |
| --- | --- |
| Application A · sector A | `private-id-A` |
| Application B · sector B | `private-id-B` |
| Application C · sector A | `private-id-A` |

Illustrative values. Application C receives the same identifier when it is registered in Application A’s sector. See [sector configuration](/world-id-auth/app-registration#manage-credentials-and-callbacks).

Each application receives a private identifier for its relationship with the human, giving every application a foundation for its own data practices.

## Fresh authentication {#verification}

Add fresh World ID authentication to your existing sign-in when an experience calls for stronger assurance. It brings the human into the flow at the moment that matters and gives your application a current authentication signal.

Your application decides whether the authenticated person may perform the action.

Together, durable continuity and fresh authentication create a flexible trust layer for every stage of the relationship.

## Powered by World ID {#powered-by-world-id}

People authenticate their World ID with zero-knowledge proofs without sharing the underlying identity or proof with your application. The World ID issuer makes the authentication result available through OpenID Connect (OIDC).

OIDC delivers the private identifier as the pairwise `sub` (subject) claim. The application stores the issuer and subject together to recognize the same World ID account over time.

For agent experiences, your application uses OIDC in the same way: it links the issuer and subject to its own account or grant, then issues credentials for its APIs or MCP server.

For IDKit proof integrations, use the separate [IDKit integration guide](/world-id/idkit/integrate).

## Integration guides {#start-building}

Keep your existing sign-in and add World ID for sensitive actions. For agent workflows, add a human checkpoint that requires fresh authentication before your application resumes the workflow.

### Step-up authentication

**Recommended starting point**

Require recent World ID authentication before a sensitive action, through your backend or auth server.

[Read the step-up guide →](/world-id-auth/step-up)

### Human in the loop

Require fresh World ID authentication before your application resumes an agent workflow. Your application handles any separate approval of the action. Works with your existing sign-in or World ID as your primary sign-in.

[Read the human-in-the-loop guide →](/world-id-auth/human-in-the-loop)

### Register and manage your application

Configure your OIDC client, callback URLs, and credentials in the developer portal, with optional help from a coding agent.

[Read the application registration guide →](/world-id-auth/app-registration)

### Primary sign-in

**Optional**

Use World ID as your primary or only sign-in, directly or through your auth server.

[Read the OIDC primary sign-in instructions →](/world-id-auth/connect-your-backend#primary-sign-in)

## Standards {#standards}

The World ID issuer and MCP server use the following OIDC and OAuth standards. Each environment’s discovery metadata lists its supported flows and options. The guides also explain how to apply these standards in your application.

### OpenID Connect

- [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) — authorization code flow, ID tokens, authentication freshness, and pairwise subjects.
- [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html) — issuer, endpoints, capabilities, and signing-key discovery.
- [OpenID Connect Dynamic Client Registration 1.0, sector validation](https://openid.net/specs/openid-connect-registration-1_0.html#SectorIdentifierValidation) — sector identifier documents for pairwise subjects.

### OAuth

- [RFC 6749 · OAuth 2.0](https://www.rfc-editor.org/rfc/rfc6749.html) — authorization code grants; refresh grants are available through the MCP OAuth endpoints.
- [RFC 6750 · Bearer Token Usage](https://www.rfc-editor.org/rfc/rfc6750.html) — MCP access tokens in the HTTP `Authorization` header.
- [RFC 7009 · Token Revocation](https://www.rfc-editor.org/rfc/rfc7009.html) — MCP access and refresh token revocation.
- [RFC 7523 · JWT Client Authentication](https://www.rfc-editor.org/rfc/rfc7523.html) — `private_key_jwt` authentication with RS256.
- [RFC 7636 · PKCE](https://www.rfc-editor.org/rfc/rfc7636.html) — S256 proof-key protection for authorization code flows.
- [RFC 8252 · OAuth for Native Apps](https://www.rfc-editor.org/rfc/rfc8252.html) — the loopback redirect port exception for MCP clients.
- [RFC 8414 · Authorization Server Metadata](https://www.rfc-editor.org/rfc/rfc8414.html) — MCP OAuth endpoint and capability discovery.
- [RFC 8628 · Device Authorization Grant](https://www.rfc-editor.org/rfc/rfc8628.html) — confidential-client device authentication with explicit approval.
- [RFC 9207 · Authorization Response Issuer](https://www.rfc-editor.org/rfc/rfc9207.html) — issuer identification in MCP authorization responses.
- [RFC 9470 · Authentication Step Up](https://www.rfc-editor.org/rfc/rfc9470.html) — guidance for authentication challenges that your resource server and authorization server implement.
- [RFC 9728 · Protected Resource Metadata](https://www.rfc-editor.org/rfc/rfc9728.html) — MCP resource, authorization-server, scope, and bearer-method discovery.

### JOSE

- [RFC 7515 · JSON Web Signature](https://www.rfc-editor.org/rfc/rfc7515.html), [RFC 7517 · JSON Web Key](https://www.rfc-editor.org/rfc/rfc7517.html), and [RFC 7519 · JSON Web Token](https://www.rfc-editor.org/rfc/rfc7519.html) — RS256 ID tokens, client assertions, and public key sets.
- [RFC 7638 · JWK Thumbprint](https://www.rfc-editor.org/rfc/rfc7638.html) — stable key identifiers for the World ID issuer's signing keys.

MCP clients are discovered through the current [OAuth Client ID Metadata Document draft](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/).

For agent discovery, read the [World ID issuer index](https://auth.world.org/llms.txt).
